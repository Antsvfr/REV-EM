# REV-EM Knowledge Quality

## Mission

Protect the quality of REV-EM's internal educational knowledge base.

Knowledge stored inside REV-EM may later be injected directly into the
context of the local AI.

An incorrect Knowledge Item can therefore systematically produce incorrect
answers.

Treat knowledge modifications as high-quality data changes.

## Fundamental rule

Never invent knowledge simply to populate the database.

A statement that sounds plausible is not automatically verified.

Do not generate hundreds of Knowledge Items and silently treat them as
authoritative.

## Knowledge architecture

Knowledge should be:

- atomic;
- structured;
- searchable;
- reusable;
- concise;
- understandable;
- versionable;
- attributable where possible.

Prefer structured concepts over entire textbook chapters.

A Knowledge Item should be small enough that retrieval can select it
independently.

## Recommended metadata

Important Knowledge Items should support metadata conceptually similar to:

id

domain

topic

title

aliases

keywords

summary

facts

mechanisms

formulas

examples

commonMistakes

relatedConcepts

sourceName

sourceType

sourceReference

verified

lastReviewed

version

timeSensitive

The actual schema may evolve, but provenance and verification must remain
possible.

## Verification

If provenance is missing or the content has not been validated:

verified = false

Never silently mark AI-generated content as verified.

"Generated by Claude" is not evidence that the knowledge is correct.

## Sources

Never fabricate:

- books;
- URLs;
- academic papers;
- authors;
- quotations;
- studies;
- statistics;
- citations.

If a source does not exist in the stored metadata, the assistant must not
invent one.

## Stable knowledge

Examples of relatively stable knowledge include:

- mathematical definitions;
- mathematical formulas;
- statistical concepts;
- fundamental accounting concepts;
- established finance mechanisms.

Even stable knowledge should still be reviewed for accuracy.

## Time-sensitive knowledge

Treat information such as these differently:

- market prices;
- current interest rates;
- current regulations;
- current tax rules;
- recent economic statistics;
- current company information;
- current events.

A static Knowledge Pack must never make old information appear current.

Use a field such as:

timeSensitive: true

when appropriate.

## Conflicts

Do not silently merge contradictory Knowledge Items.

When two items conflict:

1. identify the conflict;
2. compare provenance;
3. compare verification status;
4. compare versions and review dates;
5. surface the conflict during development when necessary.

Do not automatically claim one is true simply because it is newer.

## Retrieval quality

Knowledge retrieval must optimize for relevance rather than quantity.

A finance question about bonds should not retrieve unrelated EBITDA,
marketing, or statistics knowledge simply because generic terms overlap.

Prefer scoring based on:

exact concept
>
alias
>
topic
>
strong keyword
>
related concept
>
generic domain

Keep scoring understandable and testable.

## Context efficiency

Never inject the entire knowledge base into the LLM.

Retrieve only highly relevant items.

Remove duplicates.

Respect the central context budget.

Current question remains higher priority than large quantities of knowledge.

## Multilingual aliases

REV-EM supports multiple languages.

A single canonical Knowledge Item may contain multilingual aliases.

Example:

obligation
bond

may identify the same concept.

Do not duplicate the complete Knowledge Item five times merely to support
five languages unless there is a demonstrated need.

## Personal course separation

REV-EM Knowledge is general educational knowledge.

It must remain conceptually separate from:

- personal PDFs;
- user notes;
- imported courses;
- personal conversation history;
- account data.

Do not place private user information inside Knowledge Packs.

## Testing knowledge changes

When Knowledge Packs change, test:

- schema validity;
- duplicate IDs;
- missing required fields;
- broken references;
- duplicate concepts;
- missing provenance;
- verification status;
- retrieval relevance;
- irrelevant-query rejection;
- context-size impact.

## Git reviewability

Knowledge changes should be easy to inspect in Git.

A developer should be able to determine:

- what knowledge changed;
- why it changed;
- where it came from;
- whether it is verified;
- when it was reviewed.

Avoid huge opaque generated files when smaller reviewable changes are
possible.

## Demo knowledge

When creating sample data solely to test the engine, mark it clearly.

For example:

verified: false

and/or

status: "demo"

Do not allow demonstration content to silently become trusted production
knowledge.

## Final principle

The purpose of REV-EM Knowledge is not to make the assistant appear to know
more.

The purpose is to make the assistant more accurate, pedagogically useful,
traceable, and reliable.
